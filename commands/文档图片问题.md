向量数据库无法存储图片

当上传的doc、docx文档包含图片时，以下流程转换
将图片保持至服务器，并分配一个包含特定标识的公开访问链接，docker容器部署需要考虑到挂载至宿主机以实现持久化
将片段中图片的位置替换为该公开访问链接

检索时，
如果片段遇到包含特定标识的链接，则将图片对话加入上下文(模型支持图片理解)

## PRD: 文档图片支持

### 1. 背景

当前 RAG 系统在处理 doc/docx 文档时，仅提取文本段落和表格数据，完全忽略文档中的图片（图表、流程图、示意图等）。当用户上传包含有意义的可视化内容的文档时，这些信息在检索和回答中完全丢失。

### 2. 目标

| # | 目标 | 验收标准 |
|---|------|----------|
| G1 | 上传 docx 时提取嵌入图片 | 图片保存至服务器，片段文本中图片位置被替换为公开链接 |
| G2 | 图片持久化存储 | Docker 部署时图片存储挂载至宿主机，容器重建不丢失 |
| G3 | 检索时图片注入 LLM 上下文 | 检索到的片段若包含图片链接，图片以 ImageContent 形式加入模型请求 |
| G4 | 前端展示检索到的图片 | 源引用区域和回答正文中正确渲染图片，可点击放大 |

### 3. 核心流程

#### 3.1 上传阶段 — 图片提取与存储

```
用户上传 docx
    ↓
DocxParser 解析 XWPFDocument
    ↓ 遍历段落 → run → XWPFPicture
提取图片二进制 + MIME 类型
    ↓
ImageStorageService.saveImage(documentId, imageBytes, ext)
    → 保存至 {upload-storage-path}/images/{documentId}/{uuid}.{ext}
    → 返回公开 URL: /api/documents/images/{documentId}/{uuid}.{ext}
    ↓
在文本中图片位置插入标记: ![图片](/rag/documents/images/{documentId}/{uuid}.{ext})
    ↓
后续流程不变: 清洗 → 分块 → 向量化 → 存入 Qdrant
    （图片链接作为普通文本参与分块和向量化）
```

#### 3.2 检索阶段 — 图片注入

```
用户提问
    ↓
向量检索 + BM25 重排 → 得到匹配片段
    ↓
扫描片段文本，检测图片链接（正则匹配特定标识前缀）
    ↓
若有图片链接:
    ├── 将图片 URL 列表加入 SourceReference.images
    └── 如果模型支持多模态（vision）:
        读取图片二进制 → base64 → ImageContent
        构建 UserMessage(TextContent + ImageContent...)
    ↓
SSE 事件携带 sources（含 images 字段）→ 前端
    ↓
LLM 流式回答 → 前端
```

### 4. 详细设计

#### 4.1 图片标识与链接格式

- **标识前缀**: `/rag/documents/images/`（前端路由 basename + API 路径）
- **完整链接格式**: `![图片描述](/rag/documents/images/{documentId}/{uuid}.{ext})`
- **存储路径**: `{upload-storage-path}/images/{documentId}/{uuid}.{ext}`
- **检测正则**: `!\[.*?\]\(/rag/documents/images/[^)]+\)`

#### 4.2 图片文件管理

- 图片随文档上传时保存，随文档删除时清理
- 文件名使用 UUID，避免冲突和特殊字符问题
- 支持格式: png, jpg/jpeg, gif, bmp, emf, wmf（POI 可提取的常见嵌入格式）
- 大小限制: 单张图片不超过 10MB（超出记录警告但不上传失败）

#### 4.3 模型多模态支持

- 系统已有 `ImageContent.from(dataUri)` 的使用（RagController.askWithImage）
- 检索时检测 ChatModel 是否支持 vision（通过配置开关 `rag.image-to-llm-enabled`）
- 图片以 base64 data URI 形式注入 UserMessage，与文本内容一同发送
- 单次请求注入图片上限: 5 张（避免 token 消耗过大）

#### 4.4 前端展示

- **源引用卡片**: SourceReference 新增 `images: string[]` 字段，渲染为缩略图网格
- **回答正文**: MarkdownContent 通过 react-markdown 的 image renderer 处理图片链接
- **图片预览**: 点击图片使用 Ant Design Image.PreviewGroup 进行放大预览
- **加载状态**: 图片懒加载，显示占位 loading 态

#### 4.5 Docker 持久化

- 当前已有 `app-uploads:/app/uploads` volume
- images 子目录在 uploads 内，自然获得持久化，无需额外 volume 配置
- 若用户希望宿主机直接可见，可改为 bind mount: `./uploads:/app/uploads`

### 5. 限制与边界

| 项目 | 说明 |
|------|------|
| doc 格式 | HWPF 图片提取复杂度高，本期仅支持 docx；doc 格式中图片用占位文本 `[图片]` 替代 |
| PDF 图片 | PDF 图片提取需要额外处理（PDFBox 可提取但需坐标定位），不在本期范围 |
| 图片 OCR | 图片不做 OCR 文字识别，仅依赖周围文本进行语义检索 |
| 向量化 | 图片链接作为普通文本参与向量化，不使用 image embedding |
| token 成本 | 图片注入 LLM 会增加 token 消耗，通过配置开关和数量上限控制 |

### 6. 不做的事情

- 不做图片内容的向量化（image embedding）
- 不做 OCR 文字识别
- 不做 PDF 图片提取
- 不做图片压缩/格式转换
- 不做图片水印

## Implementation Plan

### Phase 1: 后端 — 图片提取与存储（核心）

#### Step 1.1: 创建 DocxParseResult 和 ImageReference 数据结构

**文件**: `src/main/java/com/mark/knowledge/rag/service/parsers/DocxParseResult.java`（新建）

```java
public record DocxParseResult(
    String text,                          // 替换图片后的文本
    List<ImageReference> imageReferences  // 提取到的图片列表
) {}

public record ImageReference(
    String imageId,      // UUID
    String documentId,   // 文档 ID
    String extension,    // png/jpg/emf 等
    String publicUrl,    // 公开访问链接
    byte[] data          // 图片二进制
) {}
```

#### Step 1.2: 改造 DocxParser 支持图片提取

**文件**: `src/main/java/com/mark/knowledge/rag/service/parsers/DocxParser.java`

- 新增重载方法 `parse(InputStream, String documentId)` 返回 `DocxParseResult`
- 遍历 `XWPFParagraph → getRuns() → getEmbeddedPictures()` 提取图片
- 为每张图片生成 UUID，构造公开链接
- 在段落文本中，将图片 run 替换为 `![图片](/rag/documents/images/{documentId}/{uuid}.{ext})`
- 保留原 `parse(InputStream)` 方法签名以兼容旧调用

#### Step 1.3: 创建 ImageStorageService

**文件**: `src/main/java/com/mark/knowledge/rag/service/ImageStorageService.java`（新建）

- `saveImage(documentId, imageId, extension, data)` → 保存至 `{upload-storage-path}/images/{documentId}/{imageId}.{ext}`
- `readImage(documentId, imageId)` → 读取图片二进制
- `deleteImages(documentId)` → 删除文档关联的所有图片
- `resolveImagePath(documentId, imageId)` → 返回文件系统绝对路径
- 路径安全校验：防止 `..` 路径遍历

#### Step 1.4: 添加图片访问 Controller 端点

**文件**: `src/main/java/com/mark/knowledge/rag/app/DocumentController.java`

- `GET /api/documents/images/{documentId}/{imageId}` → 返回图片文件
- 使用 `Resource` + `Content-Type` 响应
- 无需认证（公开访问，与 `/api/documents/public/**` 策略一致）
- SecurityConfig 中放行该路径

#### Step 1.5: 改造 DocumentService 集成图片

**文件**: `src/main/java/com/mark/knowledge/rag/service/DocumentService.java`

- `processDocument()` 中 docx 分支调用新的 `DocxParser.parse(inputStream, documentId)`
- 获取 `DocxParseResult` 后，调用 `ImageStorageService.saveImage()` 保存图片
- 在 `createSegment()` 的 metadata 中加入 `imageIds`（该片段包含的图片 ID 列表）
- 文档删除时同步调用 `ImageStorageService.deleteImages()`

### Phase 2: 后端 — 检索时图片注入

#### Step 2.1: 扩展 SourceReference DTO

**文件**: `src/main/java/com/mark/knowledge/rag/dto/SourceReference.java`

```java
public record SourceReference(
    String filename,
    String excerpt,
    double relevanceScore,
    List<String> images    // 新增: 图片公开链接列表
) {}
```

- 添加兼容性构造函数（无 images 参数时默认空列表）

#### Step 2.2: RagService 图片检测与注入

**文件**: `src/main/java/com/mark/knowledge/rag/service/RagService.java`

**toSourceReferences()**:
- 扫描 fragment 文本，用正则提取图片链接
- 填充 `SourceReference.images` 字段

**buildMessagesToSend()**:
- 新增配置项 `rag.image-to-llm-enabled`（默认 true）
- 检测上下文中是否包含图片链接
- 若包含且有图片文件：读取图片 → base64 → 构造 `ImageContent` 加入 `UserMessage`
- 单次请求图片上限 5 张，超出截断并记录警告

### Phase 3: 前端展示
